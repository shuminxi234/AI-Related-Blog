Kimi K3 技术拆解：2.8T MoE、KDA 与 Attention Residuals 意味着什么

从稀疏 MoE、Kimi Delta Attention、Attention Residuals 和低精度训练四条主线，分析 Kimi K3 的架构取舍、部署现实与开放权重意义。

Moonshot AI 于 2026 年 7 月 16 日公布 Kimi K3。官方给出的几个数字很醒目：2.8 万亿总参数、原生视觉能力、1,048,576 token（约 100 万 token）上下文，以及每个 token 在 896 个专家中激活 16 个。比“3T 级模型”这个标签更值得关注的，是 K3 如何同时处理三个互相牵制的问题：扩大模型容量、控制单次推理计算量，并让超长上下文仍具备可接受的效率。

本文不把尚未公开的细节当作定论。K3 的完整权重预计最迟于 7 月 27 日发布，因此当前可以核验的是官方技术博客、已经公开的 KDA 与 Attention Residuals 论文，以及在线 API；许可证、权重格式和真实部署成本仍应以届时的模型卡为准。

2.8T 不等于每次推理都计算 2.8T 参数#

K3 采用 Mixture of Experts（MoE）架构。可以把专家层理解为一组并行的子网络：路由器根据当前 token 选择少数专家参与计算，而不是让所有专家同时工作。官方将 16/896 的稀疏激活与 Stable LatentMoE 框架一并描述；每个 token 有效激活其中 16 个专家。

这带来两个不同维度的规模：总参数量代表模型可容纳的知识与功能容量，激活路径决定一次前向计算的主要成本。因此，不能用稠密模型的方式，把 2.8T 直接等同于每个 token 的计算量；同样也不能简单按 16 / 896 乘总参数，推导出精确的激活参数，因为嵌入、注意力、共享层和路由结构并不一定属于独立专家。

MoE 省的是计算，不会让存储与通信问题消失。完整权重仍需分布到大量设备，推理时还会发生 token 路由和专家间通信。对于多数团队，K3 更现实的使用方式仍是 API 或托管推理，而非办公室里的单机部署。“开放权重”提供了研究、微调和自建服务的可能，不代表部署门槛已经变低。

KDA：把随上下文增长的缓存改成可更新状态#

标准 Transformer 的注意力需要保留历史 token 的 Key/Value。上下文越长，KV Cache 越大，解码时访问历史信息的成本也越高。Kimi Delta Attention（KDA）走的是线性注意力路线：它维护固定大小的循环状态，新 token 到来时对状态进行读取和更新，而不是总在不断增长的缓存中做完整匹配。

KDA 的关键并非简单“压缩历史”。它从 Gated DeltaNet 的 delta rule 出发，引入更细粒度的门控，让不同通道能够以不同速度遗忘或保留信息。公开的 Kimi Linear 论文还采用混合结构，在 KDA 层之间保留完整注意力层，以弥补固定状态对精确长距离检索可能不够敏感的问题。

这是一种工程折中：线性注意力承担长序列中的高效记忆，完整注意力负责必要的全局查找。K3 将其作为 100 万 token 上下文的架构基础，但“窗口支持 1M”不等于在任意 1M 输入上都能无损召回细节。评估长上下文模型时，仍应分别测试精确检索、跨文档推理、时延与显存，而不是只看最大窗口数字。

AttnRes：让网络选择从哪一层取信息#

KDA 解决信息如何沿序列传播，Attention Residuals（AttnRes）关注的则是信息如何穿过模型深度。

传统残差连接会把上一层状态与当前层输出直接相加。它稳定且简单，但所有历史层的信息被逐级累积到同一条状态中，后面的层不能明确选择“回到哪一层”。AttnRes 将残差更新改造成对先前层输出的注意力聚合：当前层可以按输入动态选择更相关的中间表示。

完整地访问所有历史层会带来过高的内存和通信开销，因此论文同时提出 Block AttnRes，把层分组并保留块级表示，将跨层访问压缩到更可扩展的形式。论文在一个 48B 总参数、3B 激活参数的 Kimi Linear 模型上做了消融与下游验证；这些结果说明方法具备扩展潜力，但不能被直接当作 K3 全尺寸模型的独立对照实验。K3 的价值在于，它把这项研究从较小验证模型推到了 2.8T MoE 系统中。

MXFP4/MXFP8：低精度不是发布后的补丁#

K3 从监督微调阶段开始进行量化感知训练，官方描述的推理组合是 MXFP4 权重与 MXFP8 激活。与模型训练完成后再做压缩相比，量化感知训练让模型在优化过程中适应低精度误差，目标是在缩小权重占用和提高硬件吞吐的同时，减少能力损失。

但低位宽不能消除 2.8T 权重的物理规模。仅按 4 bit 粗略估算，权重本体就达到 TB 级，实际服务还需要激活、缓存、路由、通信缓冲和运行时开销。MX 格式的硬件支持、推理框架实现与并行策略，都会决定“理论上可压缩”和“生产中跑得好”之间的差距。等权重发布后，最值得检查的不是下载按钮，而是模型卡中的许可证、分片大小、推荐拓扑、内核支持和复现实测。

当前怎样使用 K3#

在完整权重发布前，开发者已经可以通过 Kimi 网页端或官方 API 使用 K3。官方 API 的模型标识为 kimi-k3；截至 2026 年 7 月 24 日，标价为缓存命中输入每百万 token 0.30 美元、未命中输入 3 美元、输出 15 美元，标称上下文窗口为 1,048,576 token。价格和可用区域可能调整，接入前应再次查看平台页面。

这里的缓存价差尤其值得工程团队注意。长代码库或大批固定文档反复进入上下文时，稳定的提示词前缀与请求组织方式会明显影响实际账单。不要只用标称输入单价做预算：应分别记录缓存命中率、输出长度、工具调用轮数和失败重试。官方称其编码工作负载的缓存命中率超过 90%，但这是官方服务中的特定流量数据，不能直接外推到每个应用。

若要做上线前验证，可先固定十到二十个真实任务，比较首次请求与重复请求的时延、费用和结果一致性。这样得到的应用侧数据，通常比一次“让模型写个小游戏”的演示更有决策价值。

如何看官方基准#

官方博客覆盖编程、终端任务、知识工作和生产力评测，说明 K3 的定位是长周期 Agent，而非只做聊天。与此同时，博客脚注明确指出：不同模型可能使用 KimiCode、Claude Code 或 Codex 等不同 agent harness；部分任务还采用特定 GPU、重校准分支或不同推理强度。

因此，基准结果适合证明“模型在工具环境中具备竞争力”，不适合压缩成一个跨模型的绝对排名。Agent 评测测到的是模型、提示词、工具、脚手架、预算和执行环境的组合。团队选型时应复用自己的代码库、权限边界和任务时限，记录成功率、重试次数、token 成本与人工返工量。

对工程师真正重要的三点#

第一，K3 展示了新的扩展组合：用更稀疏的 MoE 增加容量，用 KDA 控制长序列成本，再用 AttnRes 改善跨层信息流。创新并不只在参数量，而在这些机制能否共同稳定训练和服务。

第二，模型的“开放”需要分层理解。技术博客已经公开架构方向，KDA 与 AttnRes 有论文和代码；但截至 7 月 24 日，完整权重和最终许可证尚未落地。严谨的说法应是“宣布开放权重并给出发布时间”，而不是把尚未发生的发布写成既成事实。

第三，超大 MoE 把门槛从纯计算转向系统工程。专家并行、跨卡通信、低精度内核、KV Cache 和请求调度缺一不可。K3 是否会成为广泛可用的开源基础模型，不只取决于榜单分数，也取决于权重发布后的推理框架适配、社区复现与许可条件。

K3 最值得持续观察的问题不是“2.8T 是否赢过某个闭源模型”，而是这套稀疏专家、混合线性注意力、跨层注意力残差和量化感知训练的组合，能否在第三方环境中复现官方所展示的效率与 Agent 能力。7 月 27 日之后，真正的技术评估才刚刚开始。
